# AGENTS.md

## Scope and intent
- This repository is a REST API server in Go using Ent + PostgreSQL, with a small web UI and Swagger/OpenAPI exposure.
- Runtime entrypoint is `main.go`; data model source of truth is `ent/schema/`.

## Big-picture architecture
- `main.go` startup sequence is: load `.env` -> print banner -> initialize DB service -> auto-create schema -> run data initializer -> start Echo server.
- API routes are mounted under `/api/v1/persons` in `internal/controller/rest/personcontroller.go`.
- Web routes are mounted in `internal/controller/web/indexcontroller.go` (`/`, `/api`, `/openapi.json`, `/swagger/*`).
- Services live in `internal/service/`: `DBService` handles DB lifecycle/migrations; `PersonService` handles person use-cases.
- Domain model is schema-first: `ent/schema/person.go` and `ent/schema/phone.go`; Ent-generated files under `ent/` implement queries/mutations.

## Editable vs generated code
- Treat most files under `ent/` as generated and non-editable (`// Code generated by ent, DO NOT EDIT.`).
- Edit schema definitions in `ent/schema/*.go`, then regenerate Ent code.
- `ent/generate.go` contains the `go:generate` directive used to regenerate code.

## Core developer workflows
- Install/update deps: `go mod tidy`
- Build binary: `go install .`
- Run app directly: `go run .`
- Run installed binary helper: `./run.sh` (expects `$GOPATH/bin/smartgorest`)
- Run tests: `go test ./...`
- Refresh Swagger docs: `swag init -g main.go`
- Containerized run (app + Postgres): `docker compose up --build` or `podman-compose up --build`

## Ent schema workflow (project convention)
- Add entity skeleton: `go run -mod=mod entgo.io/ent/cmd/ent new <EntityName>`
- Regenerate Ent code after schema changes:
  `go run -mod=mod entgo.io/ent/cmd/ent generate ./ent/schema --feature sql/lock`
- Commit both schema changes (`ent/schema/*`) and regenerated artifacts (`ent/*.go`, `ent/<entity>/*`).

## Integration points and dependencies
- Database: PostgreSQL via `github.com/lib/pq` and Ent dialect `postgres`.
- DB configuration: environment variables (`DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`) loaded from `.env` and/or process environment.
- ORM/Codegen: `entgo.io/ent` (schema in `ent/schema`, generated client in `ent/client.go`).
- HTTP framework: Echo v5 (`github.com/labstack/echo/v5`).
- API docs: Swag (`github.com/swaggo/swag`, `github.com/swaggo/echo-swagger/v2`) with artifacts in `docs/`.
- Containerization: `Dockerfile` + `docker-compose.yml`.

## Current domain model snapshot
- `Person`: `first_name`, `last_name`, `age`, `email` + edge `phones`.
- `Phone`: `prefix`, `number`, `kind` enum (`cellular`, `home`, `work`).
- Initializer (`internal/db/dbinitializer.go`) seeds sample phones/persons when the database is empty.

## Go configuration
- Go version: 1.26 (see `go.mod`).
- GOROOT/GOPATH values are developer-machine specific; check with `go env` instead of hardcoding.

## Project-specific guidance for AI agents
- Prefer edits in `main.go`, `internal/*`, and `ent/schema/*`; avoid manual edits in generated Ent files unless explicitly requested.
- Preserve startup behavior when changing runtime flow: env load -> banner -> DB setup/schema -> DB init -> Echo server startup.
- If changing fields/relations, regenerate Ent code before finishing.
- Keep README commands aligned with actual repo state (`internal/` exists and is actively used).
- Prefer integration-style tests against disposable databases; avoid mocks for DB behavior. SQLite in-memory (`ent/dialect/sqlite`) is acceptable for fast tests where Postgres-specific behavior is not required.
- Do not manage the Git repository directly; propose commit messages and let the user handle commits/pushes.
